# Add a resource

Everything the app reads goes through one `Client` (`src/lib/api.ts`)
with a mock twin (`src/lib/mock.ts`), so the view, the browser suite and
the Kit run without a server. `Project` is the worked example.

1. **`src/lib/types.ts`**: the type (this file stays import-free). Modules that node runs import it as `import type { … } from "@/lib/types"` or `"./types.ts"`: a type-only import is erased, so either is fine.
2. **`src/lib/api.ts`**: methods on `Client` (a read takes `o?: ReadOptions` last and passes `o?.signal` to `c(…)`, so it can be called off), and their paths in `httpClient` (`GET /reports`, `GET /reports/:id`, `PATCH /reports/:id`). A list that can grow past a few hundred takes a query and answers a page: `reports(query?: ReportQuery): Promise<Page<Report>>`, its path `` `/reports${listQuery(query)}` `` (the filters, `sort`, `cursor`, `limit`); a short, bounded one (the tags in use) answers an array.
3. **`src/lib/mock.ts`**: fixtures (synthetic, "acme"; no real names, URLs or emails) as a second `let` beside `projects`, honouring `opts.empty`; a paged list filters, sorts with `sortRows` and cuts with `pageOf` (lib/pages.ts), as `projects` does, and fails its first later page under `opts.failMore`; and the methods on `mockClient`'s object, each starting with `await guard()` (`guard(true)` for a write) so `slow`, `fail`, `failOnce` and `failWrites` apply, and returning `structuredClone`s. If the palette should find it, add its kind to `SearchHit["kind"]` (lib/types.ts), an entry to `RECORD_KINDS` (lib/nav.tsx: its group, icon and the view one opens on; the palette lists each kind as its own group, and a kind without an entry fails to compile), and its list as another group in the mock's `search` (`rankEach([projects…, reports…], query)`), so one kind can't crowd the others out. Refuse what a server would (an empty or taken name) with `new ApiError(message, 422, "invalid", "name")`: the last argument is the field the form puts the message on.
4. **`src/lib/mock.test.ts`**: read, read one, a 404, a refused write, `fail`; for a paged list, a page and the next from its cursor, each filter, a sort both ways.
5. **`src/lib/api.test.ts`**: the paths and method of each new call against the stubbed `fetch`.
6. **The view** (see the `add-view` skill): `const reports = useResource(() => client.reports(), [], { key: "reports" })`, or for a paged list `usePages((page, signal) => client.reports({ ...listOf(asked), ...page }, { signal }), { key: listKey(asked) })` with `asked = { ...view, q: useSettled(view.q) }` (the search reads once the typing settles) and ``listKey = (v) => `reports${listQuery(listOf(v))}` `` (the key names the query, so each filter is kept on its own; pass the same `listKey(view)` to `optimistic`, `removeRecord` and the create form). Keyed, so coming back draws at once; a write that should show at once through `optimistic({ key, listKey, id, patch, write })` (lib/resource-cache.ts), which puts the old value back on refusal and throws on for `toastError`; the list's filters on the `View`, written with `setView(…, { replace: true })`), drawn with `<ResourceView resource={reports} label="Reading reports…" testid="reports" isEmpty={…} empty={…}>{(reports) => …}</ResourceView>`, which draws loading, failed (with Try again) and empty for you; create and edit in a `FormDialog` (components/form-dialog.tsx: give it `trigger`, `label`, `title`, `initial` values, `submit`, `failTitle`, `onSubmit` and the `Field`s; it does the dirty check, the busy state and puts a refusal on its field), the search and filters in a `ListToolbar` with `NothingMatches` when they leave none, one record in a `DetailPage` (back button, crumb, title, actions, the record through `ResourceView`), delete through `removeRecord()` (the confirm, the call, the cache, the toast), `returnFocusTo`/`useReturnFocus` so Back lands on the row.
7. **The rows** go in `<DataTable rows columns rowKey sort onSort onOpen label rowTestId rowProps>` (components/data-table.tsx): a `Column` has `id`, `label`, `cell`, and `sort` when its header sorts (`"server"` when the rows come sorted), `align: "end"` for numbers and dates, `from: "md"` to leave it out of narrow windows; keep the sort on the `View` with `parseSort`/`sortToString` (lib/list-keys.ts). A record's state is a `<StatusBadge tone>` and its tags `<Tag name>` (components/status-badge.tsx): a `STATE` table gives each status its tone and word, as `projects-view.tsx` does, and the filter, the form and the detail read the same table. Rows acted on together add `selection={{ selected, onChange, rowName }}` and a `BulkBar` in the toolbar's place, as `projects-view.tsx` does (bulk status with Undo, bulk delete behind a confirm). A paged list adds `rows={page.items} total={page.total} more={reports.more} focusRow={backTo}`, where `const backTo = useReturnFocus("data-report")` sits at the top of the list component; its empty state is "no records and no filter", else `NothingMatches`.
8. **`e2e/reports.spec.ts`**: the list from the fixtures; `slow=1` shows the loader, `fail=1` the error note with Try again, `empty=1` the empty state, `failOnce=1` recovers, `failWrites=1` toasts and the optimistic change goes back; for a paged list, `many=1` reaching the next page with End and `failMore=1` showing Couldn't read more with Try again; a deep link opens with `app.open({ hash: "/reports/r-1" })`; Back lands on the row.
9. **In a workspace**: a record that belongs to one (as `Project` does) has `workspace: string` on its type and `workspace?: string` on its query; the mock filters by it and keeps fixtures in both `w-acme` and `w-globex`; `listOf` puts the workspace on show (`prefs.workspace`, lib/workspace.ts) in the query, so the key names it and another workspace is another list; the list component calls `useWorkspaceId()` so it reads again on a switch, and waits while `useWorkspaces` is loading and shows Try again when it failed (as `ProjectList` does); create sends the workspace on show; a record opened from a link in another of the person's workspaces calls `pickWorkspace` (as `ProjectDetail` does). A resource that isn't a workspace's (the person's own settings, the workspaces themselves) skips this step.
10. **Who may write it**: an action per write in `ACTIONS` (`src/lib/permissions.ts`: `"report.create"`, `"report.edit"`, `"report.delete"` and the roles that may), `guard(true, "report.edit")` on the mock's writes so they are refused with a 403, `useCan(…)` around the New button, the edit form, the status control and Delete, a `mock.test.ts` case that a viewer is refused, and an `e2e` test with `params: { role: "viewer" }` that the controls aren't there.
11. **The words**: the view's words (columns, statuses, the form's labels and refusals' titles, toasts, the empty state) are keys in a new `src/lib/messages/reports.ts`, in English and Vietnamese, spread into `messages/index.ts` and read with `t()` in render (the `add-view` skill). The mock's refusal messages are the server's words and stay as the server sends them.
12. **The PR**: under Assumptions, what the task left open and you decided (fields, statuses, defaults, where the place sits); under Not done, what you left out and why.

Then `pnpm check` and the specs.
